## Step 1 — clean rebuild and true first run

The procedure in `docs/dev-instance.md` was followed top to bottom: servers stopped, database dropped
and recreated, MJ core migrated (162 migrations), `mj codegen --skipfiles`, `mj sync push`,
`mj codegen --skipdb`, MJ build, the three dependency apps migrated leaf-first (65, 14 and 6
migrations), `dev:owner`, this app migrated (1 migration) and its metadata pushed (100 created),
`dev:owner` again, app packages built, test rows pushed (7 created), servers started.

**Defects in the procedure, fixed in `docs/dev-instance.md`:**

1. **`READ_COMMITTED_SNAPSHOT` was never set.** Every MJAPI start logged `[WorkQueue] Error: Database
   transport — READ_COMMITTED_SNAPSHOT is OFF for this SQL Server database` (MJ's work-queue host
   requires it). Step 2 now turns it on after `CREATE DATABASE`; after that the start log has no
   WorkQueue error.
2. **The magic-link signing key was empty.** The doc said `MJ_MAGIC_LINK_PRIVATE_KEY` was set; on this
   instance it was empty, so MJAPI generated a new key at each start and every dev-login token and
   magic-link session died on each restart (Explorer then answered every call with HTTP 401 and
   stalled on "Taking longer than expected"). The key is now a documented one-time step (generated
   without printing it); a token minted before a restart was confirmed to work after it.
3. **"Strip any `sync` blocks" did not say how.** `mj sync push` writes `sync` blocks into every
   record file it touches; the procedure now restores the files with `git checkout -- metadata` (and
   `metadata-tests`), after confirming that the blocks are the only change.
4. **The app was built after MJAPI was started.** MJAPI loads `@mj-biz-apps/credentialing-server`
   from its `dist/`, and MJ's own build does not build this app's packages, so on a tree without
   `dist/` MJAPI would start without the app. The build now comes before the start, and the
   `mj:codegen` check is part of the procedure.

Also fixed: `pnpm run dev:owner` printed `Summary: nothing new created` right after granting the
application row (`scripts/dev/ensure-dev-owner.mjs` now counts that grant).

## How this differs from the plan as written

These decisions were made during implementation and are what was verified:

- **No `UI`-role permissions** exist on the credentialing entities, and there is no
  `metadata/entities` override file: CodeGen is configured to grant only `Developer` and
  `Integration`, so there was no `UI` row to switch off.
- **`DefaultNavItems` lists every nav item** (`Program Studio`, `Set up organization`,
  `New organization`, `Assignments`, `My Applications`) so that deep links resolve; what each user
  sees comes from their roles, and each page guards itself with `This area is not available to your
  account.`
- **Program Studio uses three data calls**: one for the program list and two when a program is
  opened (measured: 2 on opening the 12-section placeholder program).
- **Additional refusal sentences** exist beyond the plan: a blank version label, a duplicate program
  name, a duplicate credential prefix, a duplicate section number, and a record changed by someone
  else.
- **Magic links for personas are issued by the local dev Owner**, not by staff: a staff user would
  need Create on `MJ: Magic Link Invites`, and an unfiltered grant there would let staff mint invites
  for any role (`docs/isolation-read-paths.md`).
- **Test row names and expected counts**: `CRD-00 - Smoke` 1, `CRD-01 - Schema` 1,
  `CRD-02 - Version rules` 11, `CRD-03 - Standard rules` 10, `CRD-04 - Operations` 12,
  `CRD-05 - Isolation` 9, `CRD-06 - World` 2; client bundles via `test:integration`;
  `probe:isolation` 14/14.

Changes made by this verification (beyond documentation): `cred-world.2` removes its scratch
program; `ensure-dev-owner.mjs` reports the application grant in its summary; one comment reworded in
`load-world.ts`.

## Known gaps

- **An administrator who was not set up through organization setup has no in-product way to receive
  the Credentialing `MJ: User Applications` row.** The credentialing roles may read their own
  application rows but not create one, and the application is not `DefaultForNewUser`. Organization
  setup gives the row to the new staff member; the dev world gives it to its users. How a host gives
  it to a new `Credentialing Admin` is an open product question.
- **Issuing invitations from the product is owed by a later plan.** Today links are issued only by
  the dev harness, as the local dev Owner. The constraints that plan must meet are in
  `docs/isolation-read-paths.md`, "Owed by the plan that adds invite issuing".
- **The test rows leave scratch programs in the sample organization.** `CRD-02` to `CRD-05` and the
  wire checks create run-unique `Scratch …`, `Operations …` and `Wire …` programs as the sample staff
  member (on purpose, so the checks run under staff's row filters), and several of them end with an
  Active version, which by rule cannot be deleted. On a development database they fill Staff A's
  Program Studio list (55 such programs after this run; see the screenshots). Only `cred-world.2`'s
  scratch tree is now removed.
- **A reload of Program Studio restores the last-opened program without putting `programId` and
  `versionId` back in the URL**: Explorer's saved workspace reopens the tab with its program, while
  the address bar shows `/app/credentialing/Program%20Studio`.
- **After organization setup the admin's nav label stays "Set up organization"** until the next
  page load, while the page heading already reads "New organization".
- Applications, intake, document upload, review, AI observations, committee decisions, credential
  issuance, public verification and renewals are not built yet (FRD).
